## 保存与恢复

核心流程：

```mermaid
flowchart LR
  A[可信宿主事务] --> B[区域富文本模型]
  B --> C[统一保存队列]
  C --> D[持久化原请求与当前草稿]
  D --> E[原生区域 checkpoint]
  E --> F[核验 patch 签名与规范内容]
  F --> G[重绑捕获的来源和核销作者代次]
  G --> H[持久化回执后的状态]
  H --> I[发布保存状态]
```

- 手动保存和自动保存进入同一串行队列。自动保存由宿主显式开启，默认 idle 30 秒、最长脏状态 60 秒；导入组件不会自动开始保存。
- 打开时先检查当前写权限、epoch、协议，验证私有日志签名，再读取不可变基线的 projection/revision。rootHash、layoutHash、正文摘要必须一致，不能把最新 head 当作旧草稿的基线。
- 没有待确认请求的旧基线若落后于 head，进入冲突状态。不会因为旧草稿“看起来没改”而显示已保存或悄悄追到最新版本。
- 新请求固定 checkpointId、区域内容、来源位置、引用作者及协作者代次。原请求和当时的 Yjs 状态先持久化，随后才请求原生 API；日志失败时不提交规范内容。
- 丢响应/超时后保留完全相同的准备请求。恢复时重放原请求，核验原生 `hcdsave5` patch ID、文档/epoch/基线身份及规范内容，再接受来源回执。
- 回执只确认捕获的内容。保存期间新输入和更高作者代次仍待提交；已被确认的 Bob 代次不会再计入 Alice 后来的编辑。
- 原生提交成功但回执后日志失败时保持失败状态。重试先补持久化，不能为已成功的内容再发布一个新版本。
- 权限/epoch 失效、外部版本变化、伪造回执或明确的 4xx 模型拒绝保留草稿与原请求，并停止盲目自动重试。
- drain 阶段拒绝新本地修改和新保存，清除自动保存定时器；dispose 后的迟到响应不向房间广播状态，原准备记录可供后续恢复。

## 身份与人员提及

可信宿主通过 `change` 或 `actorForOrigin` 提供鉴权后的写入身份。后者必须从服务端连接对象解析，不能信任客户端自己提交的 userId/name。真实逐包 admission 和协议守卫还要在房间接入时完成。

可见内容若在没有可信身份的事务中变化，标记为未绑定；下一名合法用户不能替这段未知输入“认领作者”。该观察摘要一并签入日志，重启后仍拒绝借用作者。只有原请求已被规范回执完整确认、当前内容也完全与其一致，才能恢复对后续合法编辑的身份观察。

人员引用复用现有 `ReferenceAuthorLedger`。保存请求携带每个 occurrence 的作者；引用账本和当前/捕获代次均写入私有日志。新增提及由真正执行该事务的人负责，而不是简单使用 checkpoint 第一名作者。普通正文保存不重复触发关联事件；本轮不启用提醒发送。

准备日志增加可选 observation/reference proof 字段。旧准备记录可按原身份结算已知请求；仍有无法证明归属的额外内容时保持未绑定，不自动提交。

- 全部 800 个前端测试、TypeScript 检查、生产和嵌入构建通过。状态机中的磁盘失败/撤权等为受控注入检查，不宣称操作系统真实磁盘耗尽或浏览器撤权验收。
- `python3 scripts/hcd-word-region-store.py --coordinator` 使用实际原生服务、鉴权 token、文档人员目录和组件源码。代理在 r2 提交后直接关闭 TCP 响应；prepare 进程结束，另一个 Node PID 从磁盘恢复同一请求，再将保存期间输入提交为 r3。
- Bob 插入的人员提及只产生一次新增关联，事件作者为 Bob；Alice 后续文本保存没有重复事件。目录候选来自原生接口，提醒标志保持关闭；这不是外部用户中心或提醒渠道上线验收。
- 实际 DOCX 的标题/正文/页眉/页脚、人员名字、原图片字节和页码缓存均回读验证；HCDZ 离线 r1/r2/r3 完全一致，原生/离线 validate 通过。
